# Kaisen API 🚀

Django REST API сервис для управления пользователями и выработки атомных привычек по методологии **Kaisen** (непрерывное улучшение). Проект оснащён асинхронной автоматизированной системой напоминаний в Telegram с контролем лимитов, умным учётом периодичности и полноценным CI/CD пайплайном.

---

## 🛠 Технологический стек

* **Backend & API:** Python 3.14 / Django 6.1 / Django REST Framework (DRF) 3.18
* **Сервер приложений & Веб-сервер:** Gunicorn / Nginx (в качестве reverse-proxy)
* **Очереди задач:** Celery / Celery Beat (минутный планировщик)
* **Базы данных & Брокеры:** PostgreSQL 16 / Redis 7
* **Документация:** OpenAPI 3 / Swagger UI / ReDoc / `drf-spectacular`
* **Качество кода:** Ruff (Linter & Formatter), Mypy (типизация)
* **Тестирование & CI/CD:** Django APITestCase / GitHub Actions (Авто-тесты и Деплой)

---

## 🏗 Архитектурные особенности и безопасность

1. **Паттерн Thin Tasks / Fat Services:** Вся бизнес-логика интеграции с Telegram API, валидации дат и фильтрации вынесена в изолированный сервисный слой (`services.py`). Файлы Celery-задач (`tasks.py`) служат исключительно лёгкими диспетчерами.
2. **Отказоустойчивый Fan-Out в Docker:** Продакшен-архитектура разделена на изолированные контейнеры. Каждую минуту планировщик **Celery Beat** (`kaisen_celery_beat`) находит ID привычек, которые пора выполнить, и веером распределяет их в Redis как сотни маленьких подзадач для воркеров **Celery** (`kaisen_celery`). Это исключает зависание очередей при масштабировании.
3. **Защита от Rate Limiting:** Для задач отправки выставлен жесткий лимит `@shared_task(rate_limit="25/s")`, что защищает бота от блокировок (бана) со стороны Telegram API за спам.
4. **Умный учёт периодичности:** Реализована фильтрация дат на уровне СУБД PostgreSQL с помощью функции `ExtractDay` и `F-выражений`. Бот отправляет уведомления строго в соответствии с интервалом дней привычки (`periodicity` от 1 до 7) без циклов на стороне Python.
5. **Оптимизированный Dockerfile (Multi-stage):** Сборка разделена на два этапа. На этапе `builder` ставится Poetry 2.x и компилируются зависимости. В финальный легковесный образ `runner` переносится только готовое изолированное виртуальное окружение `.venv`, прописанное напрямую в системный `PATH`. Сам инструмент Poetry в финальный образ не копируется.
6. **Ролевая безопасность CRUD:** Полная изоляция личного пространства. Пользователи могут управлять только своими записями (чужие эндпоинты возвращают `404 Not Found`). Суперадминистраторы (`is_superuser`) динамически получают права на чтение всей базы и редактирование скрытых полей (`user`) в обход валидаторов.

## 🚀 Установка и запуск (Локальная разработка)

### 1. Клонирование репозитория
```bash
git clone git@github.com:burmspb-code/Kaisen.git
cd Kaisen
```

### 2. Настройка виртуального окружения (Poetry)
Убедитесь, что у вас установлен Python 3.14 и Poetry:
```bash
poetry install
poetry shell
```

### 3. Настройка переменных окружения
Скопируйте пример файла конфигурации:
```bash
cp .env.sample .env
```
Заполните обязательные переменные в созданном локальном файле `.env`. Для локального запуска напрямую (вне Docker) укажите адрес хоста базы данных как `localhost`:
```env
DEBUG=True
SECRET_KEY=your-local-secret-key
ALLOWED_HOSTS=127.0.0.1,localhost

DB_NAME=kaisen_db
DB_USER=postgres
DB_PASSWORD=your_local_db_password
DB_HOST=127.0.0.1
DB_PORT=5432

TELEGRAM_BOT_TOKEN=8362235717:AAGK1jH8Yz...
ADMIN_PASSWORD=your_admin_password
```
*Примечание: Если локальная база PostgreSQL установлена прямо в операционную систему, убедитесь, что в файле `pg_hba.conf` для локальных подключений настроен корректный метод авторизации (например, `scram-sha-256`).*

## 🐳 Развёртывание на продакшен-сервере (Docker Compose + Nginx)

На боевом сервере вся инфраструктура проекта разворачивается в изолированных контейнерах. Команды `gunicorn`, `celery` и `celery-beat` запускаются системно, так как бинарники окружения автоматически проброшены в `$PATH` образа.

### 1. Подготовка окружения на сервере
В файле `.env` на удалённом сервере обязательно измените хост базы данных на имя контейнера (`DB_HOST=db`), выключите режим отладки (`DEBUG=False`) и добавьте внешний IP-адрес или домен вашего сервера в список разрешённых:
```env
DEBUG=False
ALLOWED_HOSTS=127.0.0.1,localhost,51.250.98.192
DB_HOST=db
```

### 2. Сборка и запуск контейнеров
Для очистки старого кэша анонимных волюмов и развёртывания чистой прослойки приложения выполните команду:
```bash
docker compose down -v
docker compose up -d --build
```
Docker Compose поднимете 5 связанных контейнеров: `kaisen_django` (Gunicorn), `kaisen_postgres`, `kaisen_redis`, `kaisen_celery`, `kaisen_celery_beat` и веб-сервер `kaisen-nginx`.

### 3. Инициализация Django внутри контейнера
Поскольку базы данных поднимаются чистыми, при первом деплое необходимо вручную применить миграции, собрать статические файлы для Nginx и создать администратора:
```bash
# Накатывание структуры таблиц в PostgreSQL
docker compose exec web python manage.py migrate

# Сборка всей статики проекта в общую директорию (папка синхронизирована с Nginx)
docker compose exec web python manage.py collectstatic --noinput --clear

# Создание суперпользователя (кастомная команда проекта)
docker compose exec web python manage.py csu
```

### 4. Проверка доступности
После старта проект будет доступен извне через Nginx на стандартном HTTP-порту:
* **Панель администратора:** `http://<ваш_ip_сервера>/admin/`
* **Документация API:** `http://<ваш_ip_сервера>/api/v1/schema/docs/`

## 🔄 Автоматизация CI/CD (GitHub Actions)

В проекте настроен автоматический пайплайн непрерывной интеграции и доставки, описанный в `.github/workflows/ci-cd.yml`. Любой ваш пуш в ветки `main` или `develop` запускает автоматическую цепочку:

[ Push / PR ] ➡️ [ Job 1: Линтер Ruff ] ➡️ [ Job 2: Тесты на Python 3.14 + Postgres ] ➡️ [ Job 3: Авто-деплой по SSH ]

### Требуемые секреты репозитория (Repository Secrets):
Для работы деплоя перейдите в настройки репозитория на GitHub: **Settings ➡️ Secrets and variables ➡️ Actions** и добавьте три переменных:
* `SERVER_HOST` — Публичный IP-адрес вашей виртуальной машины.
* `SERVER_USER` — Имя пользователя для подключения (например, `burm-vm`).
* `SSH_PRIVATE_KEY` — Содержимое вашего приватного SSH-ключа (`~/.ssh/id_ed25519`), сгенерированного на сервере. 

*Важно: Публичная часть этого ключа (`id_ed25519.pub`) должна быть обязательно добавлена в файл `~/.ssh/authorized_keys` на самом удалённом сервере, чтобы виртуалка разрешила пайплайну авторизоваться.*

## 🛣 Карта API Эндпоинтов

### Порядок использования токена:
После входа (`/api/v1/auth/login/`) передавайте полученный токен в заголовках всех запросов:  
`Authorization: Token your_token_value`

### 🔑 Аутентификация и Пользователи
* `POST /api/v1/users/register/` — Регистрация нового аккаунта
* `POST /api/v1/auth/login/` — Авторизация (выдача токена)
* `POST /api/v1/auth/logout/` — Выход (инвалидация токена)
* `GET /api/v1/users/profile/` — Просмотр своего профиля
* `PATCH /api/v1/users/profile/` — Изменение данных профиля (`tg_chat_id` и др.)
* `DELETE /api/v1/users/profile/` — Мягкое удаление профиля (деактивация)
* `GET /api/v1/users/` — Список всех пользователей (только для суперадминов)

### 💪 Управление привычками (Routines)
* `GET /api/v1/routines/` — Личный список привычек пользователя (с пагинацией по 5 шт.)
* `GET /api/v1/routines/public/` — Общий список публичных привычек (доступен всем без авторизации)
* `POST /api/v1/routines/create/` — Создание новой привычки с бизнес-валидацией
* `GET /api/v1/routines/<id>/` — Детальный просмотр конкретной привычки
* `PATCH /api/v1/routines/<id>/` — Редактирование параметров привычки (для админа — со сменой владельца)
* `DELETE /api/v1/routines/<id>/` — Удаление привычки из системы

## 🧪 Тестирование и Качество кода

Проект покрыт автоматическими тестами с использованием Mock-заглушек для изоляции сетевых запросов к внешним API мессенджера Telegram.

* **Проверка кода линтером (Ruff):**
  ```bash
  poetry run ruff check .
  ```
* **Запуск модульных Unit-тестов:**
  ```bash
  poetry run python manage.py test
  ```
* **Сбор покрытия кода тестами (Code Coverage):**
  ```bash
  coverage run --source='.' manage.py test
  coverage report
  ```
